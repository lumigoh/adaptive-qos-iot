# Architecture

## Agreed concept

```text
ESP32 critical ─┐
ESP32 normal ───┼─ Wi-Fi → Raspberry Pi AP/router → Ethernet → wired receiver
Bulk laptop ────┘
```

| Device | Role |
|---|---|
| ESP32 A | Simulated critical alerts, such as a fire alarm |
| ESP32 B | Normal telemetry |
| Bulk laptop | Competing traffic generated by `iperf3` |
| Raspberry Pi | Dedicated Wi-Fi AP and router; later, controlled output queues |
| Separate wired computer | Message receiver, acknowledgements, logging, and `iperf3` server |

Sensor and bulk packets cross Wi-Fi, enter the Pi, and leave its Ethernet interface
for the receiver. Acknowledgements return through the Pi to the sender.

The receiver stays on a separate computer: packets terminating on the Pi would
bypass its Ethernet output queue. Use routing between distinct Wi-Fi and Ethernet
subnets so the path remains explicit.

## Where congestion and QoS act

Later, Linux `tc` will restrict the Pi's Ethernet output to create repeatable
congestion. Fixed QoS will classify and schedule packets at that same output.
These queues act **after** the sensor's Wi-Fi transmission.

The experiment can support a gateway-QoS claim. It cannot establish Wi-Fi airtime
priority or real-world emergency-system reliability. WMM needs separate verification.

## Decide before coding

- Confirm access to two ESP32 boards, the Pi, a Wi-Fi bulk laptop, and a separate wired computer.
- Choose the firmware toolchain and record the Pi/receiver operating systems.
- Agree on addresses, ports, message identity, acknowledgements, and configuration names.

## Verify on hardware

- The Pi can operate as an AP with the available boards.
- Measured packets traverse the Pi's Ethernet output.
- The chosen controlled bottleneck, rather than another link, causes congestion.

No hardware capability or packet path has yet been demonstrated by this repository.
